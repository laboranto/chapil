# E단계 — 팝업(시트) 설계

작성 2026-09-19 / 갱신 2026-09-20 (배포 타깃 18.0 + 웹 하한 정정 반영). 베이스 `4135d4a`(fork의 목록 개편이 master에 머지됨).

스펙 근거: `20260919_UI 2차 개편.md` — "팝업 페이지: iOS처럼 아래에서 위로 올라오는
방식, 데스크탑은 정중앙 팝업. 하위 항목: 기록 양식, 설정 페이지."

## 결론 먼저

`<dialog>` + `showModal()`. feature detect를 두고, 없으면 전체 페이지로 떨어진다.

### 배포 타깃은 웹의 브라우저 하한이 아니다

`IPHONEOS_DEPLOYMENT_TARGET`(18.0으로 상향)은 **Capacitor 네이티브 앱에만** 적용된다.
README:6에 공개 데모(`chapil-demo.varmakoro.net`)가 있고 앱스토어는 "준비 중"이며
현재 설치 경로는 셀프호스팅 **웹**이다. 그 웹을 여는 브라우저는 Xcode 설정과
아무 상관이 없다. (B단계에서 배포 타깃을 "진짜 브라우저 하한"으로 단정한 것이
오류였다. `color-mix` fallback을 남긴 결론은 맞았지만 근거가 틀렸다.)

18.0 자체는 네이티브 경로에 맞는 값이다: iOS 17과 18은 **기기 지원 범위가 같고**
(둘 다 A12 = iPhone XS/XR, 2018년) A13(iPhone 11)로 올리는 건 iOS 26이다.
즉 17 대비 기기를 하나도 안 버리면서 `dialog` 15.4 / `color-mix()` 16.2 /
`transition-behavior` 17.4 / `@starting-style` 17.5를 전부 넘는다.

### feature detect를 두는 이유 — 거의 공짜라서

전체 페이지 렌더는 **딥링크 때문에 어차피 있어야 한다.** `/records/new`를 주소창에
직접 치거나 북마크로 들어오면 뒤에 깔 배경이 없으니 전체 페이지가 맞다. 즉 구형
Safari용 "fallback 경로"를 따로 만드는 게 아니라, **이미 있는 경로로 보내기만 하면
된다.** 실제 비용은 판정 6줄뿐이다.

반면 detect가 없으면 Safari 15.4 미만에서 **기록 양식과 설정이 아예 안 열린다.**
코스메틱이 아니라 기능 파손이고, 공개 데모가 걸려 있다. 6줄이면 싸다.

이 단계의 실제 작업량은 팝업 자체가 아니라 **페이지 크롬(`.topbar` `.content`
`.form-tabs`)을 시트 안에서도 쓰이게 만드는 일**(4절)과 **배경이 안 죽어서 생기는
갱신 문제**(7절)다.

## 1. 브라우저 제약 (MDN browser-compat-data 직접 확인)

| 기능 | Safari / iOS Safari | Chrome | Firefox |
|---|---|---|---|
| `dialog.showModal()` | **15.4** | 37 | 98 |
| `@starting-style` | 17.5 | 117 | 129 |
| `transition-behavior: allow-discrete` | 17.4 | 117 | 129 |

웹 접속자를 기준으로 삼으면 `@starting-style`(17.5)은 **쓰지 않는다.** 진입
애니메이션은 **안쪽 래퍼의 CSS `animation`**으로 낸다 — 요소가 나타날 때 그냥 돌고,
`@starting-style` + `allow-discrete` 조합보다 선언이 짧으며, 미지원 브라우저에서
"애니메이션만 없고 시트는 뜬다"로 곱게 degrade한다.

## 2. 라우팅 — background location

시트는 배경 화면 위에 뜬다. 지금은 `/records/new`로 가면 `/`가 언마운트되므로
배경이 없다. react-router 표준 레시피를 쓴다.

```jsx
// App.jsx
const location = useLocation()
const bg   = location.state?.background
const page = bg ?? location          // 배경에 그릴 위치

<Routes location={page}> ... 기존 라우트 전부 ... </Routes>
{bg && (
  <Routes>
    <Route path="/records/new"                  element={<Sheet><RecordForm /></Sheet>} />
    <Route path="/records/fuel/:id/edit"        element={<Sheet><FuelForm /></Sheet>} />
    <Route path="/records/maintenance/:id/edit" element={<Sheet><MaintenanceForm /></Sheet>} />
    <Route path="/records/other/:id/edit"       element={<Sheet><OtherForm /></Sheet>} />
    <Route path="/settings"                     element={<Sheet><Settings /></Sheet>} />
  </Routes>
)}
```

`location.state`는 **새로고침·딥링크·Capacitor 콜드스타트에서 null**이다. 그때는
`bg`가 없어 시트 라우트가 안 그려지고 전체 페이지가 뜬다 — 딥링크의 올바른 동작이자,
구형 Safari가 떨어질 자리이기도 하다. 경로가 하나라 따로 만들 게 없다.

### feature detect는 dialog가 아니라 *링크*에 건다

`showModal`이 없는데 `state.background`를 넣으면 **열리지 않는 dialog로 가버린다.**
그래서 판정은 진입점에서 한다.

```js
// src/sheet.js
export const canSheet =
  typeof HTMLDialogElement !== 'undefined' &&
  typeof HTMLDialogElement.prototype.showModal === 'function'

// 시트로 띄울 곳으로 이동할 때 이 state를 실어 보낸다.
// canSheet가 false면 undefined라 그냥 전체 페이지로 이동한다.
export const sheetState = (location) => (canSheet ? { background: location } : undefined)
```

진입점 **3곳**에 전달한다:

| 곳 | 현재 | 바꿀 것 |
|---|---|---|
| `AddButton.jsx` | `navigate('/records/new')` | `navigate('/records/new', { state: sheetState(location) })` |
| `Home.jsx` 설정 `<Link to="/settings">` | — | `state={sheetState(location)}` |
| `RecordsList.jsx`의 `onOpen={() => navigate(EDIT_PATH[r.src](r.id))}` | 평범한 navigate | 같은 처리. 화살표 함수 한 군데 |

### `showAdd`가 배경을 따라야 한다

`App.jsx`의 `showAdd = location.pathname === '/'`는 그대로 두면 `/records/new`에서
`false`가 되어, **시트가 올라오는 순간 배경의 + 버튼이 사라진다.** `page.pathname`을
봐야 한다.

```js
const showAdd = page.pathname === '/'
```

### 닫기는 항상 라우트로

`dialog.close()`를 직접 부르지 않는다. 부르면 URL이 시트와 어긋난다.

- Esc → `cancel` 이벤트 → `preventDefault()` 후 `navigate(-1)`
- 백드롭 탭 → `navigate(-1)`
- 브라우저 뒤로 → 라우트가 바뀌며 컴포넌트가 언마운트 → dialog도 사라짐

**닫기 애니메이션은 v1에서 넣지 않는다.** 닫기가 라우트 언마운트로 일어나므로
`animationend`를 기다릴 시점에 React가 이미 DOM에서 지운 뒤다. 제대로 하려면 라우트
전이를 지연시키는 별도 장치가 필요한데, 열릴 때만 움직여도 충분히 읽힌다.
어색하면 그때 붙인다.

## 3. Sheet 컴포넌트

```jsx
// src/components/Sheet.jsx
export default function Sheet({ children }) {
  const ref = useRef(null)
  const navigate = useNavigate()

  useEffect(() => {
    ref.current.showModal()
    // showModal()은 iOS Safari에서 배경 스크롤을 막아주지 않는다.
    // overflow:hidden을 걸면 iOS는 스크롤 위치를 잃으므로 되돌려준다.
    const y = window.scrollY
    document.body.style.overflow = 'hidden'
    return () => { document.body.style.overflow = ''; window.scrollTo(0, y) }
  }, [])

  const close = (e) => { e.preventDefault(); navigate(-1) }

  return (
    <dialog ref={ref} className="sheet-dialog"
            onCancel={close}
            onClick={(e) => { if (e.target === ref.current) close(e) }}>
      <div className="sheet">{children}</div>
    </dialog>
  )
}
```

`e.target === ref.current`는 **백드롭 영역 클릭**을 뜻한다. 안쪽 `.sheet`를 누르면
target이 달라서 안 닫힌다.

## 4. CSS

### 함정 세 개 (이 단계가 깨지는 경로의 대부분)

1. **`dialog:not([open]) { display: none }`이 UA 규칙이다.** `display: flex`를 조건 없이
   쓰면 닫힌 dialog가 보인다. 반드시 `dialog[open]`에만.
2. `<dialog>`에는 UA `max-width: calc(100% - 6px - 2em)` / `max-height`가 걸려 있다.
   전체 화면 투명 껍데기로 쓰려면 둘 다 풀고 `border/padding/background`도 지운다.
3. `.topbar`가 `position: fixed; top: 0; left: 50%; translateX(-50%)`다. **top layer
   안에서도 fixed는 뷰포트 기준**이라, 시트 안에 그대로 두면 헤더가 시트가 아니라
   화면 꼭대기에 붙는다. 모바일에선 얼추 맞지만 데스크탑 중앙 팝업에서는 어긋난다.

```css
/*** 팝업 시트 ***/
.sheet-dialog {
  border: none; padding: 0; background: none;
  width: 100%; max-width: none; height: 100%; max-height: none;
}
/* UA가 닫힌 dialog에 display:none을 걸므로 display는 [open]에만 쓴다 */
.sheet-dialog[open] { display: flex; justify-content: center; align-items: flex-end; }
.sheet-dialog::backdrop { background: rgba(0, 0, 0, 0.4); }

.sheet {
  display: flex; flex-direction: column;
  width: 100%; max-width: var(--size-layout); max-height: 92vh;
  background: var(--surface); color: var(--on-surface);
  border-radius: var(--radius-lg) var(--radius-lg) 0 0;
  overflow: hidden;
  animation: sheet-up 0.28s ease;   /* @starting-style 불가(17.5) → animation으로 */
}
@keyframes sheet-up { from { transform: translateY(100%); } }

@media (min-width: 701px) {         /* 기존 .btn-add가 쓰던 경계와 같은 값 */
  .sheet-dialog[open] { align-items: center; }
  .sheet { max-height: 86vh; border-radius: var(--radius-lg); animation: sheet-in 0.2s ease; }
  @keyframes sheet-in { from { opacity: 0; transform: scale(0.96); } }
}
@media (prefers-reduced-motion: reduce) { .sheet { animation: none; } }
```

### 시트 안 페이지 크롬 오버라이드 — **여기가 E의 진짜 작업량**

`.topbar` `.topbg` `.content` `.form-tabs`는 전부 "뷰포트에 고정"을 전제로 쓰였다.
시트 안에서는 "상자 안의 흐름"이 돼야 한다. 딥링크·구형 브라우저용 전체 페이지
렌더가 남아 있으므로 **원래 규칙도 그대로 살아 있어야 한다** — 그래서 전부 `.sheet`
하위 선택자로 덧씌우는 순수 추가다.

| 선택자 | 페이지에서 | 시트 안에서 |
|---|---|---|
| `.topbar` | `fixed`, safe-top 반영 | `sticky top:0`, `left/transform` 해제, safe-top 불필요 |
| `.topbg` | 상단 블러 띠 | `display: none` (시트 안엔 비칠 배경이 없다) |
| `.content` | `padding-top: safe-top+64px` (고정 헤더 자리) | `overflow-y: auto`, padding-top 축소 |
| `.form-tabs` | `sticky top: safe-top+80px` | `sticky top: <시트 헤더 높이>` |
| `.sheet` 바닥 | — | `padding-bottom: var(--safe-bottom)` |

값은 구현하면서 눈으로 맞춘다. 구조만 미리 못 박아둔다.

## 5. HIG 확인 결과 (developer.apple.com 1차 출처, playwright로 직접 열람)

- **"한 번에 시트 하나만."** 시트 안에서 다른 시트를 열어야 하면 먼저 것을 닫으라고
  명시한다. → **`/import`, `/feedback`은 페이지로 남긴다.** 설정 시트에서 그리로
  가면 시트가 닫히고 페이지가 뜬다. 애매했던 부분인데 출처로 정리됐다.
- **취소는 선행 가장자리, 완료는 후행 가장자리**, 완료는 작업이 끝나기 전엔 비활성.
  `RecordForm`/`Settings`의 `.topbar`가 이미 정확히 그 배치다(✕ 왼쪽, 저장 오른쪽).
  **헤더 내용은 손대지 않아도 된다.**
- Liquid Glass는 여전히 **컨트롤·내비게이션 레이어 전용**이고 콘텐츠 레이어에는
  표준 머티리얼을 쓰라고 한다. 시트 본문은 폼 콘텐츠이므로 `--surface`(불투명)로
  간다. B단계에서 내린 결론과 같다.
- iOS 27에서 달라진 문구는 안 보인다. 다만 "사용자가 기기 설정에서 **Liquid Glass의
  선호 모양**을 고르면 variant 외형이 달라질 수 있다"는 대목이 새로 있다 —
  웹앱에서 감지할 방법이 없으니 참고만.

## 7. 시트가 새로 만드는 문제 — 배경이 안 죽는다

지금은 기록을 만들거나 고치거나 지우면 `navigate('/')`로 **Home이 리마운트**되면서
목록과 요약이 다시 읽힌다. 시트가 되면 배경 `/`가 계속 살아 있으므로 그 공짜
갱신이 사라진다. **삭제만의 문제가 아니라 생성·수정·삭제 전부의 문제다.**

fork가 넘겨준 상태:
- `usePaginatedList`의 `removeRecord`는 **남아 있다**(지금은 소비자 없음).
- `Home`의 `loadDashboard` useCallback도 남아 있다.
- `RecordsList`의 `onMutate` prop은 빠졌다 — 다시 달아야 한다.
- `DeleteRecord.jsx`가 `navigate('/')`를 직접 한다. 시트 안에서는 "닫기"가 아니라
  배경까지 날리는 전환이 된다.

갈림길 (E 착수 전에 정한다):

| 안 | 방법 | 대가 |
|---|---|---|
| A | 모듈 하나(`recordsRevision.js`) + `useSyncExternalStore`. 변경 시 카운터를 올리고 `Home`이 `RecordsList`의 `key`와 `loadDashboard`의 의존성으로 쓴다 | 목록이 리마운트돼 1페이지로 돌아간다 — 50행 너머를 보고 있었다면 위치를 잃는다 |
| B | 삭제는 `removeRecord`로 행만 빼고, 생성·수정은 리마운트 | 배선이 둘로 갈린다. 다만 수정 후 바뀐 값이 화면에 반영돼야 하므로 결국 리마운트가 필요하다 |

현재 기울기는 **A**. `useSyncExternalStore`는 React 18 내장이라 의존성이 안 늘고,
"기록이 바뀌면 목록을 다시 읽는다"는 규칙이 하나로 끝난다. 위치 유실은 데이터가
수십 건인 앱에서 실제로 밟기 어렵고, 밟더라도 B가 수정 케이스를 못 덮는다.
